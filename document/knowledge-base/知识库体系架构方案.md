# 门户网站知识库体系（Knowledge Base System）架构方案

> 版本：v1.0 ｜ 适用读者：产品 / 运营 / 管理层 + 研发团队 ｜ 配套文档：《通用检索系统产品方案》《rag方案》
> 定位：本文是检索系统的"**内容侧组织规范**"。检索系统解决"怎么把知识取出来用得准"，本文解决"知识怎么分类装进去、谁来装、各类怎么处理"。两者一前一后，构成完整的知识中台。

---

## 一、定位与设计目标

### 1.1 为什么需要"知识库体系"

《通用检索系统产品方案》已经把底层的接入、解析、检索、同步链路打通了。但对一个**面向所有行业的 SaaS 门户**而言，光有检索引擎还不够——成千上万个不同行业的租户会往里塞各种各样的内容（公司介绍、产品参数、客服问答、行业报告、营销文案……），如果没有一套清晰的**内容组织体系**，就会出现三个问题：

- **用户不知道东西该往哪放**：一份"产品说明书 PDF"到底算文档还是算产品数据？放错地方，检索就用错方式，答案就错。
- **每类内容该怎么处理没有规范**：录入要不要分块？多久更新一次？质量怎么衡量？全凭经验，无法规模化。
- **知识越堆越多但无法治理**：哪些知识在被用、哪些已经过期、哪些是垃圾，全是黑箱。

知识库体系就是要给出一套**与行业无关、可复用、可治理**的组织方式：把知识切成几个清晰的"内容板块"，每个板块配一套标准的"生命周期处理流水线"（录入 → 加工 → 评估 → 更新 → 调用），让任何行业的用户都能按图索骥地把内容存进来，系统也能自动用正确的方式处理和治理它。

### 1.2 设计目标

1. **分类清晰，人人会存**：任何一份内容，用户都能在 10 秒内判断它属于哪个知识板块（提供归属判据/决策树）。
2. **各得其法**：每类内容自动套用对应的解析、分块、检索、同步策略——用户只管"放对地方"，处理方式由体系决定。
3. **全生命周期可控**：每条知识都有明确的状态（草稿 → 待评估 → 已发布 → 待更新 → 已归档），录入、更新、评估都有标准动作。
4. **质量可评估、可治理**：知识不是"存进去就完事"，而是持续被打分、被复用度排序、被陈旧度预警，差的自动下线。
5. **行业无关、可扩展**：新增一个行业无需改架构；新增一类内容形态有标准接入步骤。

### 1.3 三条设计原则

- **按"内容形态"分类，而非按"行业/业务"分类**：内容形态（是文档、是问答、还是数据库字段）决定了它的处理方式；而行业、业务用途是**元数据标签**，不参与一级分类。这样才能做到"一套体系服务所有行业"。
- **统一生命周期，差异化处理**：所有知识共用同一套五阶段生命周期框架，但每个阶段的**具体动作**因内容形态而异。
- **存得简单、治理在后台**：对用户暴露极简的录入入口；复杂的解析、评估、同步全部由体系在后台自动完成。

## 二、知识库体系总览

整个体系可以从三条正交的轴来理解：**内容形态分类轴**（知识分成哪几类）、**生命周期轴**（每类知识经历哪些阶段）、**治理轴**（贯穿全局的元数据与质量）。

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                          知识库体系（Knowledge Base System）                      │
│                                                                                │
│  ── 分类轴：按内容形态切分的 6 大知识板块 ──────────────────────────────────────  │
│                                                                                │
│   ①文档知识      ②问答知识     ③结构化数据    ④内容资产    ⑤网络知识   ⑥行业知识   │
│   Documents      FAQ          Structured     Content      Web         Industry  │
│   公司介绍/手册   客服Q&A       产品/价格/库存   文章/新闻/   行业动态/   报告/标准/  │
│   /白皮书/说明书  /流程引导      /SKU字段       营销/详情    竞品监控    书籍       │
│       │             │             │             │            │           │       │
│  ─────┴─────────────┴─────────────┴─────────────┴────────────┴───────────┴────  │
│                                                                                │
│  ── 生命周期轴：每个板块的内容都走同一条五阶段流水线 ──────────────────────────────  │
│                                                                                │
│   [录入] ──► [加工] ──► [评估] ──► [发布/索引] ──► [检索调用] ──► [更新/再评估]     │
│   采集接入   解析分块   质量审核    建立索引        被业务消费      增量同步        │
│   /结构化映射          /合规去重                                  │              │
│                                                                  ▼              │
│                                                          [归档 / 下线]          │
│                                                                                │
│  ── 治理轴：贯穿全局 ──────────────────────────────────────────────────────────  │
│   统一元数据(行业/租户/标签/时效/权限)  ｜  知识资产目录  ｜  质量评估与健康度评分    │
│   ｜  权限与多租户隔离  ｜  知识资产飞轮（生成内容回流）                            │
└──────────────────────────────────────────────────────────────────────────────┘
                                     │
                                     ▼  （对接）
                        《通用检索系统》：统一检索能力层 + 应用编排层

```

**与检索系统的对应关系**：本体系的 6 大板块，正是检索方案里 5 类数据源的"用户视角重组"——把原方案中合在一起的"门户结构化业务数据 ④a/④b"显式拆成了独立的**③结构化数据**和**④内容资产**两个板块，因为它们对用户而言是完全不同的两件事（填表格 vs 写文章），处理方式也根本不同（MCP 直查 vs 向量+倒排）。

## 三、按内容形态的知识分类体系

### 3.1 六大知识板块定义

| 板块 | 一句话定义 | 典型内容（跨行业举例） | 本质特征 | 对应检索方案数据源 |
|---|---|---|---|---|
| **①文档知识** Documents | 成篇的非结构化正式文档 | 公司介绍、发展历程、白皮书、产品手册、说明书、资质证书、制度规范 | 排版复杂、需高保真解析、相对稳定 | ①企业基础文档 + ④a静态轨 |
| **②问答知识** FAQ | 一问一答的结构化问答对 | 客服高频问答、退换货流程、操作指引、政策解读 | 问答成对、要求精确稳定命中、高确定性 | ③FAQ问答 |
| **③结构化数据** Structured | 数据库里的字段型记录 | 产品参数、价格、库存、SKU、上下架状态、订单、会员等级 | 字段化、强实时、要筛选/排序/计数 | ④a门户结构化业务数据 |
| **④内容资产** Content | 成段的长文本内容 | 文章正文、新闻稿、营销文案、产品图文详情、案例、博客 | 自然语言、要语义理解、高频更新、可再生产 | ④b门户内容型数据 |
| **⑤网络知识** Web | 来自外部网址的网页内容 | 行业动态、竞品官网、新闻资讯、政策公告 | 来源在外、需清洗、需定时抓取 | ②Web网页 |
| **⑥行业知识** Industry | 深度专业的行业资料 | 行业研究报告、国家/行业标准、专业书籍、技术规范 | 专业深、篇幅大、需多级摘要与图谱 | ⑤行业知识库 |

> 第 7 类——**衍生知识（生成内容回流）**：内容生成模块产出的营销页/文案，会以"④内容资产"的形态回流入库，不单列为板块，但在治理层用 `source=generated` 标记，见 §7.3 知识资产飞轮。

### 3.2 归属判据：一份内容到底进哪个板块

用户最常困惑的是"这份东西该放哪"。给出一个**两步决策法**：

**第一步——问数据从哪来、长什么样：**

```
                          一份新内容要入库
                                  │
       ┌──────────────┬──────────┼───────────┬──────────────┐
       ▼              ▼          ▼           ▼              ▼
   是外部网址？    是数据库里     是一问       是上传的       是成段写出来的
                  的字段记录？   一答？       文件？         正文内容？
       │              │          │           │              │
       ▼              ▼          ▼           ▼              ▼
   ⑤网络知识      ③结构化数据   ②问答知识   看篇幅与用途↓   ④内容资产
                  （走MCP）    （qa分块）        │
                                         ┌──────┴───────┐
                                         ▼              ▼
                                   正式文档/手册      深度行业报告/
                                   /制度/说明书        标准/书籍
                                         │              │
                                         ▼              ▼
                                    ①文档知识        ⑥行业知识
```

**第二步——关键追问（解决最易混淆的三组）：**

| 容易混淆的情况 | 关键追问 | 判定 |
|---|---|---|
| 产品说明书 PDF：算文档还是结构化数据？ | 用户问的是"理解一段说明文字"还是"查某个字段值"？ | 文字语义 → **①文档知识**；参数/价格/库存字段 → **③结构化数据**。同一产品两类数据**拆两个板块**。 |
| 产品图文详情：算内容资产还是结构化数据？ | 是"成段的卖点/评测正文"还是"规格参数表"？ | 长文本 → **④内容资产**；参数表 → **③结构化数据**。 |
| 行业报告 PDF：算文档还是行业知识？ | 是"本企业自己的资料"还是"需要多跳对比的深度外部专业资料"？ | 企业自有正式文档 → **①文档知识**；需 RAPTOR 摘要+图谱的深度专业资料 → **⑥行业知识**。 |

> 核心口诀（沿用检索方案）：**"问题是筛选/排序/计数某条记录的字段，还是理解一段文字的语义？"** 前者进③走 MCP，后者进①④⑥走 RAG。
> 万能口诀（运营版）：**"查字段"走③（数据库直查），"理解文字"走①④⑥（语义检索），"标准问答"走②，"外部网页"走⑤。**

### 3.3 分类维度：一级看形态，标签记行业

为了做到"行业无关"，行业与业务用途**不进一级分类**，而是作为**统一元数据标签**附着在每条知识上：

- **一级分类（决定处理方式）**：6 大内容形态板块，固定不变。
- **元数据标签（决定可见性与过滤）**：`industry`（行业，如汽配/医疗/教育）、`tenant_id`（租户）、`business_tag`（业务用途，如售前/售后/营销）、`scene`（场景，如客服/内容生成）、`timeliness`（时效等级）、`access_level`（权限）。

这样，"汽配行业某租户的售后 FAQ"与"医疗行业另一租户的售后 FAQ"走的是**同一条②问答知识处理流水线**，只是元数据标签不同、互相隔离——这就是一套体系服务所有行业的关键。

### 3.4 门户网站信息架构视角：典型栏目 → 知识板块映射（运营配置速查）

§3.1 是"按内容形态"的技术视角，但**用户是按门户栏目来想内容的**——他想的是"公司介绍栏目""产品中心""新闻中心""帮助中心"，而不是"这是 naive 分块还是 qa 分块"。所以必须给出一张**门户栏目 → 知识板块**的映射表，让运营按自己熟悉的网站结构就能把内容放对地方。**这张表就是运营在后台给每个栏目"分配分类"时的对照手册。**

下表覆盖各行各业门户网站几乎都有的通用栏目（不分行业）：

| 门户典型栏目 | 内容样例 | 归属知识板块 | 处理方式要点 |
|---|---|---|---|
| 关于我们 / 公司介绍（网页正文） | 简介、发展历程、企业文化、团队、资质荣誉 | ④内容资产（网页正文）/ ①文档知识（上传文件） | 父子分块，稳定低频更新 |
| 关于我们（上传的介绍文件） | 公司画册 PDF / PPT | ①文档知识 | 上传的正式文件，DeepDoc 解析 |
| 公司新闻 / 动态（自有发布） | 自己后台写的新闻稿 | ④内容资产 | 自有长文本，钩子秒级同步 |
| 行业资讯 / 转载（外部来源） | 抓取/转载的外部网页 | ⑤网络知识 | Firecrawl 清洗 + 定时爬取 |
| 产品 / 服务中心（参数） | 规格参数、价格、库存、SKU、型号 | ③结构化数据 | 走 MCP 实时直查，不进 RAG |
| 产品 / 服务详情 | 图文详情、卖点、评测、使用场景 | ④内容资产 | 向量+倒排混合，CDC 秒级同步 |
| 解决方案 | 行业方案、应用案例、技术架构 | ④内容资产 + ⑥行业知识 | 混合检索 + 图谱辅助 |
| 服务支持 / 帮助中心 | 常见问题、操作指引、退换货流程 | ②问答知识 | qa 分块 + 高阈值强命中 |
| 下载中心 | 白皮书、产品手册、说明书、资质证书 | ①文档知识（+ ③静态轨 meta_fields） | DeepDoc 高保真，元数据硬过滤 |
| 案例 / 客户故事 | 成功案例、客户评价 | ④内容资产 | 语义检索，作内容生成素材 |
| 政策 / 标准 / 法规 | 行业标准、合规条款、白名单 | ⑥行业知识（+ ①文档） | laws 分块 + RAPTOR/GraphRAG |
| 联系我们 / 网点 | 地址、电话、门店、分支机构 | ③结构化数据 | 字段直查，可叠加地理过滤 |
| 招聘 · 职位列表 | 职位、要求、福利字段 | ③结构化数据 | 字段走 MCP |
| 招聘 · 职位描述(JD) | JD 正文段落 | ④内容资产 | 成段正文，走 RAG |

> 提示：**一个栏目可能拆成两个分类**。最典型是"产品中心"——参数表进 ③、图文详情进 ④；"招聘"——职位字段进 ③、JD 正文进 ④。后台允许一个栏目配置多个分类规则。
> 落地建议：录入向导按"门户栏目"组织入口（用户选栏目），系统在后台自动映射到正确的知识板块与处理流水线——**用户讲栏目，系统懂板块**。

### 3.5 多维分类视角：一份内容的五个标签轴

同一份内容可以从多个角度被分类。一级分类（内容形态）决定**处理方式**，其余维度作为**元数据标签**决定检索过滤、时效策略与隔离。把五个角度叠起来看，才能精确描述一条知识：

| 分类角度 | 取值 | 作用 | 决定了什么 |
|---|---|---|---|
| **① 内容形态**（一级） | 文档/问答/结构化/内容资产/网络/行业 | 决定解析、分块、检索方式 | **处理流水线** |
| **② 门户信息板块** | 关于/产品/新闻/帮助/方案/案例/政策… | 对齐网站信息架构 | 录入入口、栏目级权限 |
| **③ 时效等级** | 实时 / 小时 / 每日 / 静态 | 决定同步频率与陈旧度阈值 | 更新机制、预警线 |
| **④ 确定性要求** | 高确定（客服）/ 高发散（内容生成） | 决定检索双模参数 | 向量权重、阈值、Rerank |
| **⑤ 行业 + 租户** | 制造/电商/医疗/教育/政务…+ tenant_id | 决定可见范围与隔离 | 多租户过滤、行业适配 |

一个例子——"某医疗器械门户的产品说明书 PDF 里的保修条款"可被同时标注为：①文档知识、②下载中心、③静态、④高确定性、⑤医疗+租户 t_307。这五个标签共同决定了它"怎么被处理、怎么被检索、谁能看到"。

```
                       一条知识 = 5 个分类标签的叠加
   ┌─────────────┬─────────────┬───────────┬─────────────┬──────────────┐
   │ ①内容形态    │ ②信息板块    │ ③时效     │ ④确定性     │ ⑤行业+租户    │
   │ (决定处理)   │ (决定入口)   │ (决定同步) │ (决定检索)   │ (决定隔离)    │
   └─────────────┴─────────────┴───────────┴─────────────┴──────────────┘
        ▲ 一级分类               └──────── 元数据标签，正交叠加 ────────┘
```

### 3.6 跨行业适配：同一套体系，不同侧重

"面向各行各业"不是说每个行业都一样，而是**同一套 6 板块 + 五维标签框架适用所有行业，只是各板块的权重和侧重不同**。下表展示框架在典型行业门户上的落地差异：

| 行业门户 | 重头板块 | 典型内容与处理侧重 |
|---|---|---|
| **制造 / 工业品** | ③结构化数据 + ①文档 | 海量 SKU/规格走 MCP；产品手册/资质走文档高保真解析 |
| **电商 / 零售** | ③结构化数据 + ④内容资产 + ②问答 | 商品/价格/库存实时直查；详情/评测做内容；退换货 FAQ 强命中 |
| **医疗 / 健康** | ①文档 + ⑥行业知识 + ②问答 | 说明书/合规文档高保真；诊疗标准/指南上图谱；导诊 FAQ 高阈值防错 |
| **教育 / 培训** | ④内容资产 + ②问答 + ⑥行业知识 | 课程/资讯做内容；招生答疑 FAQ；考纲/政策入行业知识 |
| **政务 / 公共服务** | ②问答 + ⑥行业知识（法规） + ①文档 | 办事指南 FAQ；政策法规 laws 分块+图谱；表格/公文文档解析 |
| **金融 / 保险** | ⑥行业知识 + ②问答 + ③结构化 | 条款/合规深度知识；产品答疑 FAQ；费率/额度字段直查（强合规） |
| **B2B / 企业服务** | ④内容资产 + ⑥行业知识 + ①文档 | 解决方案/案例做内容与素材；行业洞察上图谱；白皮书文档 |
| **本地生活 / 服务业** | ③结构化数据 + ②问答 | 门店/服务/价格字段直查；预约/退改 FAQ |

> 关键结论：**接入一个新行业门户，无需改架构**——只需按 §3.4 把该行业门户的栏目映射到 6 板块、打上 `industry` 标签、按 §3.6 调整各板块投入比重即可。这正是 SaaS"一套体系、千行百业"的根本。

## 四、统一知识生命周期模型

所有板块的知识，无论形态如何，都走同一条**五阶段闭环**。这是体系的"骨架"，差异只体现在每阶段的具体动作（§五逐板块展开）。

### 4.1 五阶段闭环

```
   ┌────────┐   ┌────────┐   ┌────────┐   ┌──────────┐   ┌────────┐
   │ ①录入   │──►│ ②加工   │──►│ ③评估   │──►│ ④发布索引 │──►│ ⑤调用   │
   │ Ingest │   │Process │   │Evaluate│   │ Publish  │   │ Serve  │
   └────────┘   └────────┘   └────────┘   └──────────┘   └───┬────┘
        ▲                          │                          │
        │                          │(不合格退回)               │
        │                          ▼                          ▼
        │                    [草稿/打回修改]            [被客服/内容生成消费]
        │                                                     │
   ┌────┴─────────────────────────────────────────────────┐  │
   │ ⑥更新与再评估 Update  ◄────────────────────────────────┘  │
   │  增量同步 / 陈旧度预警 / 反馈回流 / 健康度重算            │
   └────┬──────────────────────────────────────────────────┘
        │（失效/过期/低质）
        ▼
   ┌────────┐
   │ 归档下线 │  Archive / Retire（调和清理失效 Chunk）
   └────────┘
```

### 4.2 五阶段通用定义

| 阶段 | 做什么 | 通用动作 | 产出 |
|---|---|---|---|
| **①录入** | 把内容搬进来 | 选板块 → 填元数据 → 上传/连接源 → 选触发方式（手动/定时/推送） | 原始知识单元 + 元数据 |
| **②加工** | 变成可检索单元 | 解析、分块、结构化映射、Embedding、写元数据字段 | 标准化 chunk / 工具接口 |
| **③评估（入库前）** | 把好质量关 | 解析质量检查、去重、合规审核、敏感信息过滤、人工/自动抽检 | 通过 → 进发布；不通过 → 退回 |
| **④发布/索引** | 让它可被检索 | 写入向量库 / 倒排索引 / 元数据索引 / 图谱，状态置"已发布" | 在线可检索知识 |
| **⑤检索调用** | 被业务用起来 | 被智能客服（确定性模式）/ 内容生成（发散模式）/ 开放 API 调用 | 答案 / 素材 + 调用埋点 |
| **⑥更新与再评估** | 保持新鲜与高质 | 增量同步、陈旧度预警、用户反馈回流、健康度重算、低质下线 | 更新后的知识 / 归档记录 |

### 4.3 知识状态机

每条知识都有明确状态，便于治理与审计：

```
 [草稿 Draft] ──提交──► [待评估 Pending] ──通过──► [已发布 Published] ──变更──► [待更新 Stale]
      ▲                      │                         │                          │
      └──────打回────────────┘                         │                          │
                                                  ┌─────┴──────┐            ┌──────┴──────┐
                                                  ▼            ▼            ▼             ▼
                                            [被调用中]    [低质预警]    重新加工→评估    [已归档 Archived]
```

### 4.4 状态转换的后台操作入口

状态机定义了"知识应该在哪个状态"，后台需要为每个状态提供明确的操作按钮，让运营清楚"当前该做什么"。操作按钮应随状态动态变化——同一条知识在不同状态下只显示当前可执行的操作，而不是所有状态都展示同样的按钮。

| 当前状态 | 可执行操作 | 执行后状态 | 触发逻辑 |
|---|---|---|---|
| **草稿 Draft** | 「提交审核」 | → 待评估 | 运营手动提交，进入入库前门禁流程 |
| **待评估 Pending** | 「通过发布」 | → 已发布 | 所有必选门禁项通过后按钮解锁；有未通过项则灰显并提示原因 |
| **待评估 Pending** | 「打回修改」+ 填写原因 | → 草稿 | 人工审核不合格，或门禁自动未通过退回 |
| **已发布 Published** | 「归档下线」+ 二次确认 | → 已归档 | 手动执行；或系统健康度连续低于 60 触发自动提示 |
| **待更新 Stale** | 「触发同步/重新学习」 | → 待评估 | 重新拉取最新内容，重走加工+评估流程 |
| **待更新 Stale** | 「归档下线」 | → 已归档 | 内容已确认失效，不再更新 |

> **检索启用开关（独立于状态机）**：在知识资产管理中，每条知识还有一个独立于生命周期状态的"是否参与检索"开关。这允许运营在不改变状态的前提下临时暂停某条已发布知识参与检索（如内容有争议、临时下架），或在某条知识发布前预加载索引但暂不对外可见。开关关闭时，知识保持"已发布"状态但不进入检索结果；状态归档时开关自动关闭。

## 五、各知识板块的生命周期处理详解

下面逐板块说明"录入怎么做、加工怎么做、更新怎么做、评估怎么做、检索怎么调"。这是用户最关心的"每类内容不同处理方式"的落地。

### 5.1 ①文档知识（Documents）

正式、排版复杂、相对稳定的非结构化文档。

- **录入**：用户在后台上传 PDF/DOCX/PPTX，选板块"文档知识"，填元数据（行业/标签/时效）。默认手动、低频触发；可绑定对象存储（S3/WebDAV）做定时增量。
- **加工**：DeepDoc 高保真解析（版面识别 DLR + 表格识别 TSR，物理剔除页眉页脚），`naive`/`presentation` 分块，**开启父子分块**（父块 1024/2048 token 保语义，子块 128/256 token 保精度）。
- **评估**：解析质量抽检（表格是否被切碎、是否串页）、重复文档去重、合规/版权审核。低质解析打回，可改用其他分块模板重试。
- **更新**：以稳定为主。绑定外部存储时走 **Tier 1 指纹比对**（ETag/LastModified + content_hash diff），未变更短路跳过；源端删除走 `KeyRecord(deleted=True)` 调和清理。
- **检索调用**：向量 RAG 为主（向量权重 0.3、阈值 0.2），子块命中、回溯父块上下文。

### 5.2 ②问答知识（FAQ）

一问一答、要求百分百稳定命中的高确定性问答。

- **录入**：XLSX/CSV/TXT 批量导入成对问答，或客服后台单条新增。客服后台发布即调 REST API 增量覆盖。
- **加工**：**必须用 `qa` 分块**，防止问与答被切到不同块；运营手动追加"推荐问/近义词/业务用途"，写入关键词索引权重。
- **评估**：答案准确性人工审核、近义词覆盖度检查、与既有 FAQ 冲突检测（同问不同答预警）。
- **更新**：客服后台发布即 API 增量覆盖，秒级生效；定期清理过期流程类问答。
- **检索调用**：倒排强命中为主，**关闭 Rerank 防漂移、提高阈值（0.3）**，让口语化近义提问也稳定命中标准答案。

### 5.3 ③结构化数据（Structured）

数据库里的字段型记录，要精确、可排序、可计数、强实时。**不进向量库**。

- **录入**：连接只读库 / 配置 MCP `search_products` 类工具，定义受 enum 约束的字段 Schema（category/brand/price/stock/sort_by/limit…）。低时效附件（说明书/资质）另走①文档静态轨。
- **加工**：**不分块**。通过 MCP 服务暴露参数化查询接口；LLM 仅作"受约束参数提取器"，MCP 内部用 ORM 参数化拼 SQL 查只读库。
- **评估**：字段 Schema 合法性校验、enum 枚举完整性、查询结果准确性回归测试、慢查询监控。
- **更新**：**实时直查（0 延迟）** 为主；静态 RAG 兜底轨用 **Tier 2 游标差分**（`update_time >= :checkpoint`）增量。
- **检索调用**：数据库 MCP（Function Calling）。典型信号词："最贵/最新/前 5 个/有几款/库存多少/在售的"。

### 5.4 ④内容资产（Content）

成段长文本，要语义理解、高频更新、且能被二次生产。

- **录入**：来自 CMS 内容表（articles/news/marketing/详情）。通过 CDC/数据库钩子监听，自动入库；也支持手动粘贴。
- **加工**：抽长文本 → 净化富文本 HTML/Markdown → **父子分块** → Embedding；标题/作者/标签/发布时间进倒排与 `meta_fields`。
- **评估**：内容质量（原创/完整度）、敏感词与合规审核、与产品实体的关联正确性、重复/洗稿检测。
- **更新**：**CDC/钩子 → 秒级 push**（`upload` 覆写 + `run` 强制入队，10 秒就绪）；游标轮询兜底；过期营销文案到期自动下线。
- **检索调用**：**向量 + 倒排混合**——向量负责语义召回，倒排负责标题/实体（型号/品牌）精确命中并加权。

### 5.5 ⑤网络知识（Web）

来源在外部、需清洗、需定时抓取的网页。

- **录入**：配置目标 URL / 站点，设置刷新频率（如 `Refresh Freq:1440` 每日一次）。
- **加工**：Firecrawl 调度无头浏览器，把动态页面降维为纯净 Markdown，自动剔除导航/广告/Cookie 弹窗；`naive` 分块。
- **评估**：抓取成功率、清洗后正文完整度、来源可信度标注、反爬/失效链接监控。
- **更新**：定时增量爬取 + 指纹 diff，未变更页面短路跳过。
- **检索调用**：向量 RAG（向量权重 0.4、阈值 0.2），多用于内容生成的竞品/行业动态素材。

### 5.6 ⑥行业知识（Industry）

深度专业、篇幅大、需多跳推理的行业资料。

- **录入**：上传行业报告/标准/书籍 PDF，或绑定外部知识源定时增量（如 `Refresh Freq:60`）。
- **加工**：`laws`/`book` 分块，**开启 RAPTOR 多级递归摘要**（支持"先看摘要再下钻"）+ **GraphRAG 实体关系图谱**。
- **评估**：权威性/时效性核验（标准是否被新版替代）、摘要质量抽检、图谱实体准确性。
- **更新**：绑定外部源增量轮询；旧版标准被替代时标记过期并下线。
- **检索调用**：向量 RAG（向量权重 0.5）+ 知识图谱辅助，支撑跨标准对比与多跳行业分析，主要服务内容生成（发散模式）。

### 5.7 各板块处理方式速查表（含举例）

| 板块 | 录入触发 | 加工方式 | 更新机制 | 评估重点 | 主检索方式 | 📌 处理举例 |
|---|---|---|---|---|---|---|
| ①文档知识 | 手动上传/对象存储 | DeepDoc + 父子分块 | 指纹比对(静态) | 解析保真/去重/版权 | 向量 RAG | 上传《产品手册.pdf》→ 剔除页眉页脚、表格转 HTML、父块(整段)+子块(精确)→ 问"保修多久"命中子块、返回整段 |
| ②问答知识 | 批量导入/后台发布 | `qa` 分块 + 人工标签 | API 增量覆盖(秒级) | 答案准确/近义覆盖/冲突 | 倒排强命中(高阈值) | 录"问:怎么退货 答:7天无理由"+近义词"退款/退单"→ 用户说"想退单"也命中标准答案 |
| ③结构化数据 | 连库/配 MCP | 不分块，MCP 工具 | 实时直查 + 游标增量 | Schema/枚举/慢查询 | 数据库 MCP | 连产品表 → 问"博世销量前5滤清器"→ 按品牌筛、按销量排、取5条精确返回 |
| ④内容资产 | CDC/钩子/手动 | 净化 + 父子分块 | 钩子 push(秒级)+轮询兜底 | 质量/合规/洗稿/关联 | 向量+倒排混合 | 发布产品评测 → 保存瞬间入库 → 问"噪音大不大"语义命中相关段落+原文链接 |
| ⑤网络知识 | 配 URL + 定时 | Firecrawl 清洗 | 定时增量 + 指纹 diff | 抓取率/正文完整/可信度 | 向量 RAG | 配竞品 URL 每日刷新 → 清洗成纯净正文 → 内容生成时作竞品对比素材+出处链接 |
| ⑥行业知识 | 上传/绑定外部源 | RAPTOR + GraphRAG | 外部源增量轮询 | 权威/时效/图谱准确 | 向量 + 图谱辅助 | 上传《行业白皮书》→ 生成多级摘要+实体图 → 问"A标准和B标准差异"做跨文档对比 |

### 5.8 加工阶段的进阶增强能力（按板块可选启用）

前 §5.1–5.6 是各板块的**默认加工方式**，已能覆盖绝大多数场景。对少数高价值、强逻辑或高召回要求的知识，加工阶段可**按板块可选启用**以下增强能力（成本更高，不默认全开）：

| 增强能力 | 解决什么问题 | 适用板块 | 怎么做 |
|---|---|---|---|
| **语义感知分块（Meta-Chunking）** | 固定长度 / 父子分块会在"逻辑连贯段落恰好跨越边界"处割裂语义 | ①文档、⑥行业、④内容（强逻辑长文） | 用轻量模型逐句算困惑度(PPL)，在 PPL 曲线**局部极大值**（逻辑断层处）切分；切完对每块做**语义补全**：补齐缺失的前提 / 背景，并生成一句"全局 + 局部"增强摘要随块索引 |
| **反向问题生成（Doc2Query）** | 用户口语提问与库中陈述性长文"非对称"，直接匹配召回不稳 | ②问答、④内容 | **离线**为每个 chunk 预生成若干"它能回答的虚构问题"，与原文一并索引；用户提问先匹配虚构问题、再回溯原文。离线预处理**不增加实时延迟** |
| **Embedding 模型选型** | 向量决定语义召回的上限，选错则召回口径偏 | 全部走 RAG 的板块（①④⑤⑥） | 中文 / 垂直领域优先领域模型；维度越高表达越强但存储与检索成本上升，需权衡；**与 Reranker 成套评估、统一升级**，避免版本漂移导致召回—精排口径不一致 |

> 原则：默认加工方式**够用即可**；仅当某板块出现"长文逻辑被切碎""口语提问召不回"等具体问题时，再针对性开启对应增强，用成本换质量。检索侧的查询改写、重排序、生成调参等能力属于检索系统职责，详见《通用检索系统产品方案》与《rag方案》。

## 六、知识质量评估体系

评估是体系区别于"普通文件堆"的关键——知识不是存进去就完事，而是要被持续打分、排序、预警。评估分三个时点。

### 6.1 入库前评估（准入门禁）

阻止低质内容污染知识库。每条知识发布前必须通过：

| 检查项 | 适用板块 | 不通过处置 |
|---|---|---|
| 解析质量（无串页/表格未碎） | ①④⑥ | 退回，换分块模板重试 |
| 重复/洗稿检测 | ①④ | 合并或拒绝 |
| 合规与敏感信息过滤 | 全部 | 脱敏或拒绝 |
| 答案准确性人工审核 | ② | 打回修改 |
| Schema/枚举合法性 | ③ | 修正配置 |
| 版权/来源可信度 | ⑤⑥ | 标注或拒绝 |

#### 6.1.1 门禁检查结果的后台展示

门禁检查不应是黑箱——每条知识的检查结果需要在后台明确呈现，让运营知道"卡在哪、该怎么处理"。

- **逐项列出通过/未通过状态**：在知识详情页（或审核弹窗），每个门禁检查项显示 ✅ 通过 / ❌ 未通过 / ⬜ 待确认三种状态。
- **未通过时给出处置建议**：每个未通过项附上对应动作（"换分块模板重试"、"人工确认答案准确"、"脱敏后重新提交"等），避免运营不知道下一步做什么。
- **「通过发布」按钮的解锁条件**：仅当所有必选检查项均通过（含人工确认项）时按钮才可点击；否则灰显并提示待解决项数量。
- **人工审核项需显式确认**：如 FAQ 答案准确性，须运营在后台勾选"已人工审核，确认无误"方可标记为通过，不能自动通过。

示例——FAQ 知识「退换货流程」的门禁检查面板：

| 检查项 | 适用此类知识 | 当前状态 | 处置建议 |
|---|---|---|---|
| 合规与敏感信息过滤 | ② | ✅ 通过 | — |
| 答案准确性人工审核 | ② | ⬜ 待确认 | 请确认答案内容准确后勾选通过 |
| 重复 / 冲突检测（同问不同答） | ② | ✅ 通过 | — |

### 6.2 运行期评估（在线反馈）

知识发布后，用真实使用数据持续评判它"好不好用"：

- **命中表现**：被检索召回次数、命中后被采纳为答案的比例、引用可溯源率。
- **用户反馈**：客服答案的赞/踩、内容生成对素材的采用/丢弃、人工纠错次数。
- **陈旧度**：距上次更新时长 vs 该板块时效等级阈值（如③结构化超 1 小时未同步即预警，⑤网络超刷新周期未抓取即预警）。
- **覆盖盲区**：检索"无结果/低分被阈值丢弃"的查询聚类，暴露知识缺口，反向驱动补录。

#### 6.2.1 陈旧度的后台展示

陈旧度不只是一个"待更新"状态标签，后台应提供足够上下文，让运营理解"为什么是陈旧的、有多严重"：

- **时效等级 + 已超期时长**：在知识详情页和资产列表中同时展示"时效等级（如：每日）"与"距上次更新已过 X 天（超出阈值 Y 天）"，让运营直观判断紧迫程度。
- **不同板块的陈旧阈值参考**：
  - **④内容资产**：发布后 10 分钟内未入库（钩子未触发）即预警
  - **③结构化数据**：实时直查，通常无陈旧问题；游标差分轨道超 1 小时未运行预警
  - **⑤网络知识**：超刷新周期（如 24 小时）未成功抓取即预警
  - **①文档知识**：静态内容超 90 天未更新进入"关注"（阈值可按板块配置，见 §8.3）
  - **②问答知识**：超 30 天无更新且有差评时进入"关注"
- **批量陈旧视图**：概览页"需要处理"待办项中，"内容过期/待更新"应支持按板块展开，让运营快速定位哪些板块的内容集中偏旧。

### 6.3 周期性评估（知识资产健康度评分卡）

定期（如每周）为每条/每类知识算一个**健康度综合分**，驱动治理动作：

```
健康度 = 质量分(解析/准确/合规)  ×30%
       + 时效分(新鲜度/同步及时)  ×25%
       + 复用分(被调用频次/被多模块复用) ×25%
       + 反馈分(赞踩比/纠错率)    ×20%

  ≥80 健康   → 保持，可推荐为优质素材
  60~80 关注 → 提示更新/补充近义词/重解析
  <60 预警   → 进入待整改；连续低分自动归档下线
```

> 复用分 / 反馈分越高的知识，在内容生成时越优先被当作"优质素材"调用——评估结果反哺检索排序，形成正循环。

#### 6.3.1 健康度的后台展示：分解而非黑盒

健康度评分对运营的价值在于"知道该做什么"，而非只看一个数字。后台展示应满足：

- **四维分解展示**：在知识详情页显示各维度的得分与权重，而不只是一个综合总分。示例：`质量 29/30 · 时效 18/25 · 复用 21/25 · 反馈 16/20 = 综合 84`。
- **低分维度给出建议动作**：
  - 时效分低 → 提示"距上次更新 X 天，已超过该板块时效阈值，建议触发同步/重新学习"
  - 质量分低 → 提示"解析质量不达标，建议重新学习或更换分块模板"
  - 复用分低 → 提示"近 30 天被检索调用较少，考虑补充近义词或确认内容相关性"
  - 反馈分低 → 提示"用户差评率偏高，建议查看调用记录排查原因"
- **统一颜色编码**：≥80 绿色（健康）、60–79 橙色（关注）、<60 红色（预警）；概览板块健康度条、资产列表、详情页三处统一配色，运营一眼识别问题。
- **"关注"和"预警"知识的主动推送**：概览页"需要处理"待办项中应聚合低健康度知识（<60 预警条数），点击可跳转到按健康度排序的资产列表，快速批量整改。
- **目录内可交互体检**：知识资产目录以“体检任务”承载检测。运营点击“新建体检任务”后，列表进入范围选择状态，可先按板块、来源方式、行业等条件筛选，再勾选知识、全选当前筛选或全选全部；提交后任务异步运行。任务和结果作为“体检记录”长期保留，运营可在任意已完成任务中查看检测范围、创建/完成时间、页面上下文、检查前后健康度、问题原因和建议动作。单条结果详情提供补路由、补结构化字段、同步、重新学习、标记已更新、下线等可执行操作；执行修复后刷新知识状态、更新时间、健康度及该任务中的诊断结果，形成“任务诊断 → 修复 → 再评估”闭环。

### 6.4 监测与评估技术体系（Langfuse + RAGAS + OpenTelemetry）

前三节定义了"评什么"，本节定义"用什么评、怎么落地"。整套监测与评估能力由三个开源组件协同构成，分工明确、互补不重叠：

| 组件 | 角色 | 在体系中负责 | 许可/成本 |
|---|---|---|---|
| **OpenTelemetry (OTel)** | 链路追踪标准 | 统一埋点协议，把一次问答的全链路串成 trace（数据采集的"管道"） | CNCF 开源，免费 |
| **Langfuse** | 可观测 + 评估平台 | 接收 trace、存评测数据集、跑评估、出看板（数据汇聚的"大脑"） | MIT 开源，**自托管永久免费**（仅付服务器成本） |
| **RAGAS** | RAG 评估算法库 | 计算 faithfulness / answer relevancy / context precision / context recall 等指标（评估的"标尺"） | 开源，免费 |

> 选型理由：本系统是**自托管、多租户、面向全行业**的 SaaS，租户数据不得外流，因此选 **Langfuse 自托管**（数据不出域）而非 LangSmith（闭源 SaaS，自托管仅企业版、成本高且数据上云）。三者均为开源免费，总成本仅为自建服务器投入。

#### 6.4.1 集成位置：在编排层埋点，不侵入 RAGFlow

监测能力**接在 AgentScope 编排层（应用层），而非 RAGFlow 内核**。AgentScope 原生集成 OpenTelemetry + Langfuse SDK，把一次问答的各环节包成 span 上报，RAGFlow 的检索调用作为其中一个 span：

```
[门户用户提问]
     │  注入全局 X-Request-Trace-ID（OTel 上下文贯穿全程）
     ▼
┌────────────────── AgentScope 编排层（OTel 埋点） ──────────────────┐
│  span: 意图识别 → span: 检索(调 RAGFlow Retrieval API / MCP)       │
│        → span: 上下文组装 → span: LLM 生成(首字延迟)               │
└───────────────────────────┬───────────────────────────────────────┘
                            │ OTLP 协议上报
                            ▼
                      [ Langfuse 自托管 ]
              · Trace 看板：树状耗时拓扑，秒级定位瓶颈
              · 数据集：沉淀真实问答为评测样本
              · 评估：调用 RAGAS / LLM-as-Judge 打分
              · 在线反馈：客服赞/踩、人工纠错回流（对接 §6.2）
```

#### 6.4.2 三层评估的落地映射

把 §6.1–6.3 的评估时点，对应到具体工具实现：

| 评估层 | 对应章节 | 落地工具与做法 |
|---|---|---|
| **解析/分块质量** | §6.1 入库前 | RAGFlow chunk 可视化抽检 + 脚本规则（空块率/超长块/重复率/表格完整率），不达标打回重切 |
| **检索质量** | §6.2 命中表现 | 建黄金测试集（按 6 板块分别建），调 RAGFlow **Retrieval API** 批量回归，算 **Hit Rate@k / Recall@k / MRR / 命中平均相似度**；结果写入 Langfuse 看板 |
| **端到端答案质量** | §6.2 + §6.3 | Langfuse 上跑 **RAGAS**：faithfulness（防幻觉）、answer relevancy（答非所问）、context precision/recall（检索准不准/全不全）、noise sensitivity（抗噪：被相关冗余或无关文档带偏而出错的概率，越低越好）；线上真实问答经 OTel 持续采样评估 |
| **运行期可观测** | §6.2 陈旧度/盲区 | Langfuse trace 看板 + 告警：检索超时、首字延迟、"无结果/低分丢弃"查询聚类（暴露知识缺口） |

#### 6.4.3 评估指标与健康度评分卡的衔接

RAGAS / 检索回归算出的指标，不是孤立报表，而是**回灌到 §6.3 健康度评分卡**：检索命中率、引用可溯源率 → 进"质量分"；Langfuse 采集的赞/踩、纠错率 → 进"反馈分"；调用频次 → 进"复用分"。每周由 Langfuse 拉取数据重算健康度，驱动知识的保持 / 整改 / 下线，形成"评估 → 治理 → 再评估"闭环。

#### 6.4.4 落地节奏建议

投入产出比最高的顺序：① 先在 AgentScope 打通 OTel + Langfuse 自托管，拿到线上 trace 与延迟基线；② 建 50 条高频问题的黄金集，脚本调 Retrieval API 算 Hit Rate@5 / MRR 作为检索基线，每次调分块/参数都对比；③ 客服上线后接 RAGAS 做端到端答案质量评估；④ 把指标接入健康度评分卡，实现自动治理。

#### 6.4.5 评测集自动生成（降低冷启动成本）

§6.4.4 第②步的黄金测试集初期靠人工整理，成本高、覆盖有限。当积累不足时，可用 **RAGAS 的评测集自动生成**从现有知识库反向造题，快速拿到可回归的基线：

1. **建知识图谱**：对知识库文档切分 → 抽取器（基于 LLM 或规则如 NER）提取信息 → 按语义相似 / 共享实体 / 层级结构建立节点关系。
2. **场景化造题**：每道题 = 节点 + 查询长度（短/中/长）+ 查询风格（搜索式/对话式）+ 人设（如新手用户 / 资深采购），覆盖真实多样的提问方式。
3. **难度分层**：区分**单跳**（单文档可答）与**多跳**（需跨 2+ 文档串联，考验⑥行业 / 方案类知识）、**具体**（查事实）与**抽象**（需归纳总结），使评测集覆盖不同复杂度。

> 用法：自动生成的题集与人工黄金集**互补**——自动集保覆盖广度、快速回归，人工集保高频真实场景的准确性；二者都接入 §6.4.3 的健康度评分闭环。

## 七、知识治理与扩展机制

### 7.1 统一元数据规范（Knowledge Schema）

每条知识都挂一组标准元数据，是分类、过滤、权限、评估的共同基础：

| 字段 | 含义 | 示例 |
|---|---|---|
| `kb_section` | 一级板块（6 选 1） | content_asset |
| `tenant_id` | 租户隔离 | t_10086 |
| `industry` | 行业标签 | 汽配 |
| `business_tag` | 业务用途 | 售后/营销 |
| `scene` | 适用场景 | 客服/内容生成 |
| `frontend_route` | 前台页面路由，用于回答溯源和页面上下文判断 | /products/kfr-35 |
| `frontend_nav_path` | 前台导航路径 | 产品中心 / 空气滤清器 / KFR-35 |
| `page_type` | 前台页面类型 | 列表页/详情页/FAQ页 |
| `structured_fields` | 页面结构化字段 | sku, price, stock |
| `timeliness` | 时效等级 | 实时/小时/每日/静态 |
| `access_level` | 权限 | 公开/内部/受限 |
| `source` | 来源 | manual/frontend_page/generated/web |
| `status` | 生命周期状态 | published |
| `health_score` | 健康度评分 | 86 |

### 7.2 权限与多租户

SaaS 门户必须租户级隔离：检索时强制按 `tenant_id` + `access_level` 过滤；同一套 6 板块流水线被所有租户复用，但数据互不可见。知识资产目录（Catalog）让每个租户能浏览、检索、管理自己名下的全部知识资产。

### 7.3 知识资产飞轮（生成内容回流）

录入的知识不只是被"读"，还能被"再生产"：

```
录入产品/文档 → 自动进对应板块 → 内容生成调用（MCP取参数+RAG取素材）
   → 产出营销页/文案 → 以 source=generated 回流为「④内容资产」
   → 经入库前评估 → 又成为新素材，供 SEO/客服话术/其他模块复用
```

回流内容同样走完整生命周期（含入库前评估，防止低质生成内容污染），并打 `source=generated` 便于追溯与治理。

#### 7.3.1 生成回流内容的专属审核流

回流内容（`source=generated`）需要在后台有独立的标识与审核入口，而不是与普通手动录入内容混排：

- **视觉标识**：知识资产目录中，`source=generated` 的内容显示"AI 生成"标签，让运营一眼区分来源，不与 `manual`/`cms` 内容混淆。
- **专属审核队列**：在"待评估"状态的资产中，支持按 `source=generated` 过滤，形成"AI 生成待审核"子视图；运营集中审核而非逐条从全量列表里翻找。
- **审核重点不同于普通内容**：生成内容的门禁检查重点在于"内容真实性（引用是否可溯源）""品牌一致性""合规审核"，而不是解析质量（生成文本无解析问题）。门禁面板应按 `source=generated` 动态调整显示的检查项，省略不适用项（如"解析质量/表格完整性"）。
- **审核通过后的流程**：与普通 ④内容资产 完全相同——父子分块 → Embedding → 发布索引，`source=generated` 仅作来源标签保留，不影响后续处理流水线。

### 7.4 扩展性：新增行业 / 新增内容类型

- **新增一个行业**：零架构改动。只需在该租户下用 `industry` 标签录入内容，自动套用 6 板块流水线。这是"面向所有行业"的根本保证。
- **新增一类内容形态**（未来若出现如"音视频知识""代码知识"）：标准接入四步——① 定义板块与归属判据；② 配置解析/分块管道；③ 定义更新机制与时效等级；④ 接入评估指标与元数据。接入后即纳入统一生命周期。

## 八、用户操作视角：不同角色怎么往体系里存内容

体系对用户暴露的应当是**极简的录入入口 + 智能板块推荐**，复杂处理全在后台：

| 角色 | 主要往哪些板块存 | 典型操作 |
|---|---|---|
| 客服/运营 | ②问答知识、④内容资产 | 后台填问答、发文章/营销稿，发布即同步 |
| 产品/数据 | ③结构化数据、①文档知识 | 连库配 MCP、上传说明书/手册 |
| 市场/内容 | ④内容资产、⑤网络知识、⑥行业知识 | 录营销素材、配竞品监控、传行业报告 |
| 管理员 | 全部（治理） | 配权限/租户、看健康度评分卡、处置低质知识 |

**录入向导建议**：用户上传内容时，系统按 §3.2 决策树自动**推荐板块**并预填元数据，用户确认即可——把"放对地方"的认知负担降到最低。

### 8.1 配置示例：以"新闻栏"为例走一遍

运营要把"新闻栏"分到哪个板块、之后怎么处理，完整走一遍：

**第1步 · 判断分类**：新闻栏发的是自己后台写的新闻稿（成段正文、几乎每天更新）→ 查 §3.4 → 自有新闻 → **分到 ④内容资产**。（如果是转载外部网站的行业资讯，则分到 ⑤网络知识。）

**第2步 · 后台配置（运营做的唯一动作）**：
```
后台 › 栏目管理 › 新闻栏 › 知识库设置
   ├─ 分配分类：[④ 内容资产 ▾]
   ├─ 同步方式：[发布即同步（推荐）▾]
   ├─ 行业标签：[汽配]      权限：[公开]
   └─ 保存 ✓
```

**第3步 · 系统自动处理（运营无需干预）**：
```
运营点"发布"一篇新闻
        ▼
系统钩子捕获 → 抽正文 → 净化富文本 → 父子分块 → 向量化
        ▼          标题/发布时间进关键词索引
        ▼
10 秒内入库，状态=已发布
        ▼
用户在客服问"最近有什么新活动" → 向量语义命中这条新闻
        ▼
答案附带【出处：新闻栏《XX活动上线》· 发布于X月X日】可点击链接
```

**第4步 · 后续更新与评估（系统自动）**：改了这篇新闻再保存 → 自动覆盖更新；过期活动新闻 → 到期自动下线；系统持续记录这条新闻被问到多少次、答得准不准，算进健康度评分。

> 整个过程运营只做了**第2步选分类**这一次配置，其余全自动——"配一次、自动跑"。

### 8.2 后台需支持的配置项

为支撑上面的运营操作，后台"栏目知识库设置"需提供这些可配置项：

| 配置项 | 可选值 | 说明 |
|---|---|---|
| 分配分类 | ①文档 / ②问答 / ③结构化 / ④内容资产 / ⑤网络 / ⑥行业（可多选） | 决定处理流水线，**唯一必填** |
| 同步方式 | 发布即同步 / 定时同步 / 手动 | 默认按分类给推荐值 |
| 时效等级 | 实时 / 小时 / 每日 / 静态 | 影响更新频率与陈旧度预警 |
| 行业标签 | 按租户行业预填 | 多租户隔离与行业适配 |
| 权限 | 公开 / 内部 / 受限 | 检索可见范围 |
| 检索模式 | 跟随分类默认（一般不用改） | 客服=确定性，内容生成=发散 |

> 运营默认只需选"分配分类"，其余项系统按分类给出推荐默认值，做到**最少配置**。

### 8.3 数据源管理：来源通道的独立配置对象

"数据源"是运营侧管理知识来源的核心操作单元——每条知识挂在一个数据源下，数据源归属一个板块，板块决定处理方式。三层关系：**知识资产 → 数据源（运营配置）→ 知识板块（决定处理方式）**。

后台"数据源管理"需支持：

| 功能 | 说明 |
|---|---|
| **新建数据源** | 填写名称、归属板块、接入方式（前台页面/上传文件/外部网址/数据库/对象存储）、同步方式与频率 |
| **编辑数据源** | 可修改名称、同步频率、备注；归属板块不建议随意变更（会影响已入库知识的处理方式） |
| **启用/停用** | 停用后该数据源不再同步，已入库知识保留但不更新；重新启用后恢复同步 |
| **立即同步** | 对支持增量同步的数据源，可手动触发一次立即同步（不等下次定时）|
| **删除** | 删除前提示"该数据源下 N 条知识将一并移出知识库"，二次确认后执行 |
| **查看同步日志** | 进入该数据源的历史同步记录（上次/下次同步、状态、时延），对应"同步状态"栏目 |

#### 8.3.1 从前台页面批量添加内容（前台网站结构选择器）

门户网站的内容最终体现在前台导航和页面上。后台拿到的是前台网站结构：站点、导航路径、页面标题、页面路由、页面类型、绑定数据和结构化字段。运营不需要理解内部生成过程，只需要从前台页面里勾选哪些内容进入知识库。

1. **呈现前台网站结构**：按门户网站、导航路径展示全部前台页面，例如首页、产品中心、产品详情、服务支持、FAQ、下载中心、联系我们。
2. **路由进入元数据**：每条页面入库时写入 `frontend_route` 和 `frontend_nav_path`，让用户提问时能定位到"问的是哪个页面的信息"。
3. **页面数据结构化**：页面正文按内容资产处理；价格、库存、SKU、网点、FAQ 等字段型数据写入 `structured_fields`，用于元数据过滤或工具调用提示。
4. **每条页面带默认归属板块**：系统按 §3.4 映射关系为页面预填推荐板块，运营通常直接确认即可。
5. **支持逐条改板块**：若某个页面的默认推荐不合适，运营可在勾选后修改归属板块（下拉选 6 板块之一）——板块一旦确定，处理方式（分块/同步/检索）自动确定，运营无需进一步配置。
6. **入库方式跟着板块走**：板块决定同步方式（如内容资产→发布即同步，文档→手动，网络→定时），显示给运营确认，而不是让运营单独选一遍"入库方式"。
7. **批量确认**：勾选完成后一键"添加所选"，批量创建对应知识资产配置并开始入库。

> 已添加的前台页面在选择器中显示为灰色"已添加"状态，防止重复配置。

### 8.4 板块处理参数配置（高级，按需调整）

§5.7 处理速查表中的参数（分块方式、向量权重、相似度阈值、Rerank 策略）是系统默认值，覆盖绝大多数场景。对于有调优需求的租户或管理员，后台应允许按板块配置这些参数：

| 参数 | 可配置范围 | 系统默认（按板块） | 说明 |
|---|---|---|---|
| **分块方式（chunk_method）** | naive / qa / presentation / laws / book | 见 §5.7 速查表 | 决定内容如何被切分学习；普通运营通常不需改 |
| **向量权重** | 0.0–1.0 | 见 §5.7 速查表 | 向量召回与倒排召回的混合比例 |
| **相似度阈值** | 0.0–1.0 | 见 §5.7 速查表 | 低于此分数的结果被过滤；FAQ 用 0.3，其余多为 0.2 |
| **Rerank 开关** | 开启 / 关闭 | FAQ 关闭，其余开启 | FAQ 关闭防语义漂移；其余开启精排 |
| **Embedding 模型** | bge-large-zh / bge-m3 / text-embedding-3-large / gte-large-zh | 租户级统一配置 | 一般全租户统一，不按板块单独选；升级时须与 Reranker 成套（见 §5.8）|
| **进阶增强（可选开启）** | Meta-Chunking / Doc2Query | 默认关闭 | 见 §5.8；仅当该板块出现"长文逻辑被切碎"或"口语提问召不回"时再开启 |

> **最少配置原则**：这些参数系统已按板块给出合理默认值，普通运营无需触碰。建议只在出现具体召回问题时，由运营管理员在"板块详情"中按需调整，并在调整后用"问答测试"验证效果再保存。

## 附录

### A. 与检索系统的衔接

本体系是检索系统的"内容供给侧"。映射关系：本文 6 板块 → 检索方案 5 类数据源；本文"加工/检索调用"阶段 → 检索方案的"解析分块层 / 统一检索能力层"；本文"更新"阶段 → 检索方案第六章"增量同步机制"；本文"检索调用" → 检索方案"应用编排层"（客服确定性模式 / 内容生成发散模式）。

### B. 术语速查

- **知识板块（kb_section）**：按内容形态划分的一级分类，决定处理方式。
- **知识生命周期**：录入 → 加工 → 评估 → 发布 → 调用 → 更新/再评估 → 归档，七个状态的闭环。
- **健康度评分**：质量×时效×复用×反馈的综合分，驱动知识治理与素材优选。
- **知识资产飞轮**：生成内容回流入库成为新素材的正循环。
- **OpenTelemetry（OTel）**：CNCF 开源的链路追踪标准，统一埋点协议，全链路数据采集的管道。
- **Langfuse**：MIT 开源的 LLM 可观测 + 评估平台，自托管永久免费，本系统的监测大脑（数据不出域）。
- **RAGAS**：开源 RAG 评估算法库，提供 faithfulness / answer relevancy / context precision/recall 等指标。
- **Hit Rate@k / Recall@k / MRR**：检索质量量化指标——命中率 / 召回率 / 命中平均排名倒数。
- **语义感知分块（Meta-Chunking）**：用困惑度(PPL)在逻辑断层处切分、并对每块做语义补全的进阶分块方式，见 §5.8。
- **Doc2Query（反向问题生成）**：离线为每个 chunk 预生成"它能回答的虚构问题"并一并索引，以提升口语提问召回，见 §5.8。
- **noise sensitivity（噪声敏感度）**：RAGAS 指标，衡量系统被相关冗余或无关文档带偏而出错的概率，越低越好。
- **父子分块 / RAPTOR / GraphRAG / MCP / 双模调控**：详见《通用检索系统产品方案》附录。
- **数据源（DataSource）**：运营侧管理知识来源的配置单元，每个数据源归属一个板块、决定一类内容的接入方式与同步策略；一个板块可有多个数据源（如"新闻栏"和"案例栏"都属于④内容资产）。
- **检索启用开关**：独立于生命周期状态的实时控制，允许在不改变状态的前提下临时暂停/恢复某条知识参与检索；状态归档时自动关闭，见 §4.4。
- **前台网站结构选择器**：后台批量接入前台页面的交互入口，按站点、导航路径、页面路由展示页面并预填推荐板块，运营确认后批量创建知识资产配置，见 §8.3.1。
