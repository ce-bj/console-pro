# 门户网站通用检索系统（Universal Retrieval Platform）产品方案

> 版本：v1.0 ｜ 适用读者：产品 / 管理层 + 研发团队 ｜ 技术底座：RAGFlow + AgentScope + MCP

---

## 一、背景与目标

### 1.1 业务背景

本方案面向**各行各业的门户网站**（制造、电商、医疗、教育、政务、金融、B2B 服务、本地生活等），以 SaaS 形态提供一套通用的知识检索与智能应用能力。不同行业的门户栏目结构相似（关于我们 / 产品中心 / 新闻资讯 / 帮助中心 / 解决方案 / 下载中心…），但内容形态高度异构，因此需要一套"**分类清晰、各得其法、行业无关**"的处理体系。

门户网站正在从"信息展示"升级为"智能服务 + 内容生产"双引擎。当前存在两个核心诉求方：

- **前台智能客服**：用户来到网站咨询公司信息、产品规格、售后问题，需要"准、稳、可溯源"的回答，杜绝幻觉。
- **后台内容生成**：运营人员需要批量生产营销落地页、行业产品文案，需要"广、活、有素材"的知识供给。

这两类诉求都依赖同一份底层知识，但对检索的要求几乎相反（客服要确定性，生成要发散性）。同时，知识本身来自五类高度异构的数据源：文档、Web 网页、FAQ、门户自有结构化内容（数据库）、行业知识库。

**核心矛盾**：异构数据接入会带来语义失真；同一份知识又要同时满足"高确定性客服"与"高发散性生成"两种对立场景。

### 1.2 产品目标

构建一个**通用检索中台**，对上提供统一的检索/调用能力，对下统一接入并治理五类数据源，实现：

1. **一次接入，多处复用**：任意数据源接入一次，客服、内容生成、未来其他业务模块都能调用。
2. **数据自动增量同步**：后台录入/修改产品、新闻、文案后，无需人工搬运即可准实时进入知识库。
3. **检索能力可调控**：同一套底层检索，通过参数切换"确定性模式"与"发散模式"。
4. **结构化数据安全调用**：产品库等结构化数据通过受控工具调用（Function Calling + MCP）而非裸 SQL。
5. **内容可被二次生产**：录入的产品/知识可作为"原料"被内容生成模块按需调用，产出营销页、文案等再供其他模块使用。

### 1.3 衡量指标（North Star & 关键指标）

| 维度 | 指标 | 目标参考值 |
|---|---|---|
| 客服质量 | 答案命中率 / 引用可溯源率 | ≥ 90% / 100% |
| 客服性能 | 首字响应延迟 | < 1.5s |
| 数据时效 | 后台变更到知识库就绪时延 | 主动推送 ≤ 10s；轮询 ≤ 60min |
| 内容生产 | 单篇营销文案/落地页产出时长 | 由小时级降到分钟级 |
| 复用度 | 被多个业务模块调用的知识资产占比 | 持续提升 |

## 二、设计原则

1. **数据流与控制流分离**：底层检索只负责"取数"，上层智能体负责"决策"，用 AgentScope + MCP 解耦。
2. **一套检索，双模调控**：通过 `vector_similarity_weight`、`similarity_threshold`、`top_k` 等参数，让确定性客服与发散性生成共用同一底座。
3. **结构化数据不裸奔**：摒弃 Text-to-SQL，LLM 仅作"受约束的参数提取器"，真正的查询由 MCP 服务参数化执行。
4. **增量优先，全量兜底**：默认只处理"变化的单元"（指纹/游标 diff），全量重建仅作为兜底。
5. **解析质量决定上限**：分块（chunking）质量直接决定下游效果，不同数据形态用不同解析路径。
6. **可观测、可降级**：全链路 Trace + 工具熔断降级，保证生产环境不被单点击穿。

## 四、数据源分类与处理策略

这是方案的核心。五类数据源对应不同的接入、解析、检索、同步策略。

### 4.1 分类总表

| 数据源分类 | 原始格式 | 推荐分块模板 | 核心解析配置 | 检索参数（默认） | 同步机制 | 主要承载场景 |
|---|---|---|---|---|---|---|
| **① 企业基础文档** | PDF / DOCX / PPTX | `naive` / `presentation` | `layout_recognize:true`，开启父子分块 | 向量权重 0.3，阈值 0.2 | 静态同步，手动/低频触发 | 公司介绍、发展历程、白皮书 |
| **② Web 网页** | 外部 URL / 门户静态页 | `naive` | Firecrawl 清洗为纯净 Markdown，剔除导航/广告 | 向量权重 0.4，阈值 0.2 | 定时爬取（如每日 1440min），指纹 diff | 行业动态、竞品官网、新闻 |
| **③ FAQ 问答** | XLSX / CSV / TXT | `qa` | Q&A 成对解析，人工补近义词/标签 | 关闭 Rerank 防漂移，阈值 0.3 | 客服后台发布即 API 增量覆盖 | 高频客服问答、退换货流程 |
| **④a 门户结构化业务数据**（字段型） | MySQL / PG 关系表（products/sku/price/stock） | **不分块**，走 MCP 工具 | MCP `search_products` 暴露字段查询；低时效说明书走静态轨打 `meta_fields` | **数据库 MCP** 为主 + 元数据硬过滤 RAG 兜底 | 实时直查(0延迟) + 游标增量(小时级) | 产品参数、价格、库存、SKU 精确筛选/排序/计数 |
| **④b 门户内容型数据**（长文本） | DB 内容表（articles/news/marketing/详情页富文本） | `naive` + 父子分块 | 从 DB 抽长文本→HTML/Markdown 净化→Embedding；标题/标签进倒排 | **RAG 向量 + 倒排混合**（标题/实体倒排加权） | CDC/钩子→秒级 push；游标轮询兜底 | 文章正文、新闻、营销文案、公司介绍、产品详情语义问答 |
| **⑤ 行业知识库** | PDF（报告/标准/书籍） | `laws` / `book` | 开启 `raptor` 多级摘要 + `graphrag` 实体图谱 | 向量权重 0.5，开启知识图谱辅助 | 绑定外部存储增量轮询（如 60min） | 内容生成、行业分析、多跳对比 |

### 4.2 各类数据源处理详解

**① 企业基础文档（高保真解析 + 父子分块）**

用 DeepDoc 做版面识别（DLR）和表格识别（TSR），物理剔除页眉页脚噪声，把表格还原成结构化 HTML 避免被切碎。关键是**父子分块**：父块（1024/2048 token，保完整语义）+ 子块（128/256 token，保检索精度）。检索时用子块精准命中，返回时带出父块完整上下文，既准又不断章取义。

**② Web 网页（Firecrawl 自动清洗 + 定时增量）**

直接抓 raw HTML 会污染向量。用 Firecrawl 调度无头浏览器，把动态页面降维成纯净 Markdown，自动剔除导航、广告、Cookie 弹窗。配置 `Refresh Freq` 每日增量爬取，未变更页面短路跳过。

**③ FAQ（专属 qa 分块 + 人工干预）**

必须用 `qa` 模板，防止问答被切到不同块。解析后运营可手动追加"推荐问"和"业务标签"，这些会写入关键词索引权重，让口语化近义提问也能 100% 稳定命中标准答案。客服侧建议关闭 Reranker、提高阈值（0.3）以防语义漂移。

**④ 门户后台录入内容（读数据库 —— 本方案重点，必须区分两种形态）**

后台录入并存进数据库的数据，**绝不只有产品**。同一张库里既有"结构化字段"（产品参数、价格、库存），也有"长文本内容"（文章、新闻稿、营销文案、产品图文详情、公司介绍）。这两类的检索方式根本不同，必须拆开处理。

> 关键判断：**问题是"筛选/排序/计数某条记录的字段"还是"理解一段文字的语义"？** 前者走 MCP，后者走 RAG。

**④a 结构化业务数据（字段型）→ 数据库 MCP 工具调用**

适用：产品参数、价格、库存、SKU、上下架状态等"表格字段"。这类数据要的是精确、可排序、可计数、强实时。

- **动态轨（实时）**：LLM 只输出受 enum 约束的筛选参数（如 `category/brand/sort_by/limit`），MCP 服务内部用 ORM 参数化拼 SQL 查只读库，返回干净 JSON/Markdown。LLM 全程不碰 SQL，杜绝注入。**不做向量化**——把"博世浏览量最高的5个滤清器"丢给向量库只会语义乱配，必须靠字段过滤+排序。
- **静态 RAG 轨（兜底）**：低时效的产品说明书、资质证书、维保条例（本身是长文本附件），用 dlt 增量管道抽取，把分类/品牌/型号打成 `meta_fields`，检索时先元数据硬过滤再向量匹配。

**④b 内容型数据（长文本）→ RAG 向量 + 倒排混合**

适用：文章正文、新闻稿、营销文案、产品图文详情、公司介绍等"成段的自然语言"。这类用户会用模糊的自然语言问（"为什么/怎么样/有什么区别"），必须靠语义理解。

- **同步入库**：通过 CDC/数据库钩子监听内容表（如 `articles`、`news`），抽出长文本字段 → 净化富文本 HTML → 父子分块 → Embedding 写入知识库；标题、作者、标签、发布时间等进倒排索引与 `meta_fields`。
- **检索方式**：向量负责语义召回（理解"换滤芯频率"≈"多久更换"），倒排负责标题精确命中与实体（型号/品牌）硬匹配，两者**混合**。标题命中、实体命中给倒排加权，避免长文里跑题。
- **与产品的关系**：一个产品往往**同时**产生两类数据——参数表（→④a MCP）和图文详情/评测文章（→④b RAG）。同一实体按字段/正文拆到两条轨。

**⑤ 行业知识库（RAPTOR 多级摘要 + GraphRAG）**

行业报告/标准用 `laws`/`book` 分块，开启 RAPTOR 做多级递归摘要聚类（支持"先看摘要再下钻"的多跳问答），开启 GraphRAG 构建行业实体关系图谱，支撑内容生成时的跨标准对比与行业分析。

### 4.3 检索方式选型：什么时候 RAG / 倒排 / 数据库 MCP

这是落地时最容易混淆的点。三种检索方式各有擅长，**选错方式比没接入更糟**（会给出看似合理实则错误的答案）。判断顺序如下：

```
                    用户/模块发起一个查询
                            │
        ┌───────────────────┼───────────────────────┐
        ▼                   ▼                       ▼
 要的是"某条记录的       要的是"理解一段          要的是"既要语义又要
 字段/排序/计数/聚合"     文字说了什么"            精确术语/标题命中"
        │                   │                       │
        ▼                   ▼                       ▼
 ✅ 数据库 MCP         ✅ 向量 RAG             ✅ 倒排(BM25)主导
 (Function Calling)   (语义检索)              或 向量+倒排混合
```

**三者职责边界与判据**

| 检索方式 | 擅长 | 典型信号词 | 数据形态 | 不擅长 |
|---|---|---|---|---|
| **数据库 MCP** | 精确筛选、排序、计数、聚合、实时字段 | "最贵/最新/前5个/有几款/库存多少/在售的" | ④a 结构化字段 | 语义理解、模糊问法 |
| **向量 RAG** | 语义相似、同义改写、模糊自然语言、长文理解 | "为什么/怎么/有什么区别/能不能/解释一下" | ①文档 ④b内容 ⑤行业知识 | 精确计数、实时排序、型号串精确匹配 |
| **倒排(BM25)** | 精确术语、型号串、专有名词、标题精确命中、长尾低频词 | "KFR-35""GB/T 18488""退换货" | 所有文本类（常与向量混合） | 同义/口语化改写 |

> 实务上 ④b/①/⑤ 的检索几乎总是**向量+倒排混合**（见第五章四阶段流水线），区别只在权重：型号/标题类查询调高倒排权重，语义类查询调高向量权重。**纯倒排单独用**的场景主要是 FAQ 关键词强命中和精确编号检索；**纯 MCP**则是结构化字段查询，根本不进向量库。

**示例对照（同一个零件厂商场景）**

| 用户问法 | 该走哪条 | 原因 |
|---|---|---|
| "博世浏览量最高的5个空气滤清器" | **数据库 MCP** | 要筛选(品牌)+排序(浏览量)+计数(5)，纯字段操作 |
| "KFR-35 还有货吗 / 多少钱" | **数据库 MCP** | 查实时库存/价格字段，要求 0 延迟准确 |
| "空气滤清器多久换一次" | **向量 RAG**（④b内容/说明书） | 模糊语义问法，答案在文章/手册正文里 |
| "刹车片和刹车盘有什么区别" | **向量 RAG**（⑤行业知识） | 概念解释，需语义理解与多文档整合 |
| 搜型号串 "GB/T 18488" | **倒排主导** | 专有编号，精确字面匹配，向量易跑偏 |
| "退换货怎么操作" | **倒排+FAQ qa** | 高频标准问，关键词强命中标准答案 |
| "帮我写 KFR-35 的营销文案" | **MCP(取参数) + RAG(取行业素材)** | 字段走 MCP 保准确，素材走 RAG 保发散 |

### 4.4 为什么这样分类

分类的本质是按**"时效性 × 结构化程度 × 确定性要求"**三个维度切分，再叠加上面的检索选型：

- 结构化字段 + 高时效（产品/价格/库存） → 数据库 MCP（④a）
- 结构化字段 + 低时效（说明书/资质） → 元数据过滤 RAG 兜底（④a 静态轨）
- 内容型长文本（文章/新闻/营销/详情） → 向量+倒排混合 RAG（④b）
- 非结构化 + 高确定性（FAQ） → qa 分块 + 倒排强命中 + 高阈值
- 非结构化 + 强语义（文档/行业知识） → 父子分块 / RAPTOR+GraphRAG
- 外部动态（Web） → Firecrawl + 定时增量

### 4.5 门户网站信息内容的多维分类（面向各行各业）

前面 4.1 是"按数据源形态"的技术分类。但门户运营是**按网站栏目**来组织内容的，且本方案要服务各行各业，因此再补两个落地视角：**门户栏目映射**与**跨行业适配**。

**(1) 门户典型栏目 → 数据源 → 处理方式**

各行业门户的栏目高度趋同，可统一映射到上述 5 类数据源：

| 门户栏目（通用） | 内容样例 | 对应数据源 | 处理方式 |
|---|---|---|---|
| 关于我们 / 公司介绍 | 简介、历程、资质 | ①文档 / ④b 内容 | 父子分块，低频静态同步 |
| 产品 / 服务中心（参数） | 规格、价格、库存、SKU | ④a 结构化 | MCP 实时直查，不进 RAG |
| 产品 / 服务详情 | 图文详情、卖点、评测 | ④b 内容 | 向量+倒排混合，CDC 秒级 |
| 新闻 / 资讯 / 公告 | 自有新闻 / 外部行业资讯 | ④b 内容 / ② Web | 钩子 push / 定时爬取 |
| 解决方案 | 行业方案、技术架构 | ④b 内容 + ⑤ 行业知识 | 混合检索 + 图谱辅助 |
| 帮助中心 / 服务支持 | 常见问题、操作/退换货流程 | ③ FAQ | qa 分块 + 高阈值强命中 |
| 下载中心 | 白皮书、手册、说明书、证书 | ①文档（+④a 静态轨） | DeepDoc 高保真 + 元数据硬过滤 |
| 案例 / 客户故事 | 成功案例、客户评价 | ④b 内容 | 语义检索，作内容生成素材 |
| 政策 / 标准 / 法规 | 行业标准、合规条款 | ⑤ 行业知识（+①文档） | laws 分块 + RAPTOR/GraphRAG |
| 联系我们 / 网点 / 招聘 | 地址、门店、职位字段 | ④a 结构化（+④b 正文） | 字段直查，正文走 RAG |

> 落地建议：录入入口按"门户栏目"组织（运营选栏目），系统后台自动映射到正确的数据源与处理流水线——**运营讲栏目，系统懂数据源**。

**(2) 跨行业适配：同一套底座，不同侧重**

"面向各行各业"= **同一套 5 类数据源 + 双模检索框架适用所有行业，仅各类权重与侧重不同**：

| 行业门户 | 重头数据源 | 处理侧重 |
|---|---|---|
| 制造 / 工业品 | ④a 结构化 + ①文档 | 海量 SKU 走 MCP；手册/资质高保真解析 |
| 电商 / 零售 | ④a 结构化 + ④b 内容 + ③ FAQ | 价格库存实时直查；详情做内容；退换货强命中 |
| 医疗 / 健康 | ①文档 + ⑤ 行业知识 + ③ FAQ | 说明书/合规文档；诊疗指南上图谱；导诊 FAQ 高阈值防错 |
| 教育 / 培训 | ④b 内容 + ③ FAQ + ⑤ 行业知识 | 课程资讯做内容；招生答疑；考纲政策入行业知识 |
| 政务 / 公共服务 | ③ FAQ + ⑤ 法规 + ①文档 | 办事指南 FAQ；法规 laws+图谱；公文文档解析 |
| 金融 / 保险 | ⑤ 行业知识 + ③ FAQ + ④a 结构化 | 条款深度知识；产品答疑；费率额度字段直查（强合规） |
| B2B / 企业服务 | ④b 内容 + ⑤ 行业知识 + ①文档 | 方案/案例作素材；行业洞察上图谱；白皮书文档 |
| 本地生活 / 服务业 | ④a 结构化 + ③ FAQ | 门店/服务/价格字段直查；预约退改 FAQ |

> 关键结论：**接入一个新行业门户无需改架构**——把该门户栏目映射到 5 类数据源、打 `industry` 元数据标签、按行业调整各类投入比重即可。这是 SaaS"一套底座、千行百业"的根本。详细的内容组织与生命周期治理见配套《知识库体系架构方案》。

## 五、统一检索能力层（双模调控）

底层是**两阶段混合检索**，对上通过参数切换两种"人格"。

### 5.1 检索流水线（前置查询改写 + 四阶段混合检索）

```
用户/模块查询
   │
   ▼
[阶段0] 查询理解与改写：指代消解/纠错/术语对齐 →(可选)多查询/HyDE → 解析出标签过滤条件
        （详见 §5.4；客服偏改写+硬过滤，生成偏多查询+HyDE）
   │
   ▼
[阶段1] 多路初筛：向量库 ∥ 倒排库 并行召回
        融合公式 S = 0.95·向量 + 0.05·关键词，拉取 top_k=1024 候选
   │
   ▼
[阶段2] 后检索精排：S = w·余弦 + (1-w)·词频相似；w=vector_similarity_weight
        （配置专用 Rerank 模型则替代此步）
   │
   ▼
[阶段3] 阈值过滤：丢弃低于 similarity_threshold 的块（防噪声进上下文）
   │
   ▼
[阶段4] 上下文组装：父子回溯 / 元数据过滤 / 图谱扩展 → 交给 LLM
```

词频侧采用实体增强：命名实体（品牌名、型号）权重 ×3，普通名词 ×2，并做 Unigram(40%)+Bigram(60%) 多尺度打分，保证型号类硬匹配精准。

### 5.2 双模参数对照

| 模式 | 消费方 | 向量权重 w | 阈值 | Rerank | Temperature | 目标 |
|---|---|---|---|---|---|---|
| **确定性模式** | 智能客服 | 0.3（偏词频对齐） | 0.3（高） | FAQ关闭/文档开 | 0.10 | 准、稳、可溯源 |
| **发散模式** | 内容生成 | 0.5（语义均衡） | 0.2（低） | 开 | 0.85 | 广覆盖、富素材、有创意 |

**同一套底座，靠参数切人格** —— 这是"通用检索"的关键设计。

### 5.3 对外接口形态

- **Retrieval API**：`POST /retrieve`，入参含 `kb_ids`、`query`、`vector_weight`、`threshold`、`top_k`、`metadata_condition`。
- **MCP Tools**：`search_products`（结构化）、`web_search`（Firecrawl）、`kb_search`（知识库语义检索），由 AgentScope Toolkit 注册为本地可调用函数。

### 5.4 查询理解与改写（检索前置增强）

门户用户的真实提问往往简短、口语化、带指代与错字，与库中"陈述性长文档"存在**非对称检索**鸿沟。在阶段1 多路初筛之前先对 Query 做理解与改写，是提升召回性价比最高的一环：

- **Query 优化（建议默认开）**：指代消解（结合多轮上下文，"它多少钱"→"KFR-35 多少钱"）、纠错去噪（去错字与"那个…我想问下…"等口语助词）、术语对齐（口语→专业词）、长难句拆解提取核心语义。
- **多查询生成（Multi-Query，选用）**：LLM 从不同角度生成 3–5 个近义问题分别检索，"广撒网"提升召回率，防单一提问角度漏检。
- **HyDE（假设文档，选用）**：先让 LLM 凭直觉写一个"假答案"，再用假答案向量检索真实文档，把"问题→文档"非对称匹配转成"文档→文档"对称匹配——即便假答案有错，其携带的专业词也能拉近向量距离。
- **Doc2Query（反向问题，离线加工）**：入库时为每个 chunk 预生成"它能回答的虚构问题"一并索引，用户提问先匹配虚构问题再回溯原文；**离线预处理、不增加实时 RT**，特别适合 ③FAQ / ④b内容 提升口语召回。
- **标签过滤（对接 metadata_condition）**：把口语问题解析出硬标签（品牌/型号/行业/时效），叠加到 §5.3 的 `metadata_condition` 做物理硬过滤，滤掉"语义接近但事实不符"的噪声（避免 iPhone 15 Pro Max 与 iPhone 14 混淆）。

> **双模差异**：客服（确定性）优先"Query 优化 + 标签硬过滤"，慎用多查询/HyDE 以免语义发散并增加延时；内容生成（发散）适合"多查询 + HyDE"扩大素材召回。注意多查询会让后续 Rerank 计算量成倍增加（见 §5.5）。

### 5.5 重排序（ReRank）：交叉编码器精排

§5.1 阶段2 的轻量融合公式可满足多数场景；对"多条件同时满足"的复杂查询，则启用**交叉编码器（Cross-Encoder）** 重排模型（如 `gte-rerank`，对应功能清单 C4）替代该步：

- **原理**：召回阶段的文档向量与 Query 无关、预先算好，只能表达"平均语义"，故只能保证"相关"而非"精确匹配"。重排把 Query 与每个候选文档**拼成一个长句**送入模型，用交叉注意力让 Query 每个 token 直接观察文档每个 token，捕捉细微匹配。如"2000 元以下、续航好的华为手机"会被逐条核验"是否华为/是否<2000/是否提续航"，缺一项则分数跳水。
- **价值**：精度飞跃（解决"看着像但答非所问"）；作为向量与倒排(BM25)结果的统一"裁判"实现多源融合；给 LLM 的上下文更少更准，降本并缓解"中间丢失"。
- **代价与约束**：增加延时与算力；有上下文长度限制；对多查询不友好（5 个变体则计算量 ×5）。故作为**可配置开关**：客服高价值链路开启，③FAQ 强命中链路关闭防漂移（见 §4.2），发散或成本敏感链路按需限流——与 §5.2 双模表一致。

### 5.6 生成阶段的可靠性控制与调参

检索到证据后由 LLM"开卷作答"，此阶段更依赖模型的**总结能力**而非其自身知识。§5.2 已给出 Temperature 的双模取值，这里补齐生成阶段的失效防范与调参：

- **常见失效模式**：无检索结果时**捏造**答案；检索到却**未按要求作答**；多文档**知识冲突**（A 说可办 / B 说禁止）；长上下文**中间丢失**（模型对首尾敏感、忽略中部）；**忽略参考资料**改用陈旧知识作答。
- **Prompt**：强约束"无依据则拒答 / 禁用外部知识"，句末**强制标注来源**（对应客服 100% 可溯源指标）；用分隔标记隔开指令与检索切片；按问题类型套用不同模板。
- **调参**：需可复现→固定 `seed`；减少重复→调 `presence_penalty`；查事实→降 `temperature`/`top_p`，求创意→调高（呼应客服 0.10 / 生成 0.85）；`max_tokens` 按输出长度与成本权衡，过小会截断。
- **微调（SFT）**：Prompt 优化到极限仍不达标时，用"问题–参考资料–标准答案"语料做指令微调，专门训练"依据资料作答"与"资料不足时拒答"。

## 六、增量同步机制（含零件厂商示例）

门户后台高频变更，必须"只处理变化的单元"。采用**轮询 + 推送双轨**。

### 6.1 同步总流程图

```
                  [ 门户后台 CMS / 业务数据库 ]
                     /                      \
       (定时增量轮询 Checkpoint Pull)   (即时变更推送 API/Webhook Push)
          每小时 / 每日                       秒级
              │                                  │
              ▼                                  ▼
   [ 指纹/游标 diff 比对 ]            [ REST 网关 / Webhook ]
   - 文件 ETag/LastModified          - POST /document/upload (覆写)
   - DB update_time 游标             - POST /document/run    (强制入队)
              │                                  │
              └──────────────┬───────────────────┘
                             ▼
              [ RAGFlow Ingestion Pipeline ]
              - 仅对新增/修改单元做 解析+Embedding
              - 热覆盖对应 ES / 向量索引
              - 源端删除 → 调和清理失效 Chunk
```

### 6.2 两类增量路径

- **Tier 1 指纹比对（非结构化：新闻/营销文档/白皮书）**：轮询时只拉 Metadata（ETag/LastModified），与 `content_hash` 双向 diff；一致则短路跳过，变更才进管道；源端删除走 `KeyRecord(deleted=True)` 调和清理。
- **Tier 2 游标差分（结构化静态轨：MySQL 产品规格）**：用 `SyncLogs.next_checkpoint` 持久化游标，每次 `SELECT * FROM products WHERE update_time >= :checkpoint`，处理后滚动游标，免全量。

### 6.3 主动推送（秒级）

后台 CMS 发布/更新/下架时，异步 POST 到统一网关：先 `upload` 覆写文档，再 `run`（强制 `UNSTART`）插入任务队列头部，10 秒级就绪。无需落盘的临时上下文（如限时降价话术）可走 Agent Webhook，热插拔进提示词。

### 6.4 ★ 零件厂商示例（问题1：产品如何自动增量同步到 RAG）

> 场景：零件厂商在后台录入一个新产品"BOSCH 空气滤清器 KFR-35"。

```
[运营在后台保存产品]（含字段：参数/价格/库存，以及富文本：图文详情/评测文章）
       │
       ▼
[CMS 写入业务数据库] ── products 表(字段) + product_detail/articles 表(长文本)
       │
       ├──(④a 字段轨)──► 无需同步进 RAG！MCP search_products 直连只读库，
       │                  客服问"价格/库存/排序"时实时返回，0 延迟、精确
       │
       └──(④b 内容轨)──► 触发 ORM AfterSave 钩子/CDC → 异步发 Webhook
                          │  （只对图文详情、评测文章等长文本做 RAG）
                          ▼
                 POST /api/v1/document/upload  (抽长文本→净化富文本→文档)
                          │
                          ▼
                 POST /api/v1/document/run     (强制入队，跳过轮询)
                          │
                          ▼
                 Ingestion：父子分块 → 打 meta_fields(category/brand/型号)
                          → Embedding + 标题/实体进倒排 → 热写入索引
                          │
                          ▼
                 ✅ 10 秒内：详情/文章可被"向量+倒排混合"语义检索命中
```

> **要点**：同一个产品被拆成两条轨——**结构化字段不进 RAG**（MCP 实时查更准），**图文详情/文章才进 RAG**（语义问答需要）。这正是"什么时候 MCP、什么时候 RAG"在同步环节的落地。

**三种触发方式择优**：
1. **数据库钩子/CDC（推荐）**：ORM AfterSave 或 binlog 监听，对运营完全透明，零感知。
2. **CMS 主动推送**：后台保存按钮触发 API，链路最短、最实时。
3. **定时游标轮询（兜底）**：万一钩子失败，按 `update_time` 兜底补偿，保证最终一致。

## 七、内容生成调用机制（问题2：产品如何被内容生成调用）

录入的产品不仅能被检索，更是内容生产的"原料"。内容生成智能体把产品/行业知识当作可调用的素材源。

### 7.1 内容生成流程图

```
[运营 Prompt: "生成 KFR-35 空气滤清器的高转化营销落地页"]
       │
       ▼
[ ContentPlannerAgent ] 规划文案大纲，识别需要哪些素材
       │
       ├─► 调 MCP search_products  → 拉取该产品规格/参数/卖点（结构化，权威）
       ├─► 调 kb_search(行业知识库) → RAPTOR 摘要：行业趋势、技术标准
       ├─► 调 web_search(Firecrawl) → 竞品官网规格对比
       │
       ▼
[ AgentScope Code Sandbox (gVisor 隔离) ]
   - Pandas 做参数对比表 / 性能对比，Matplotlib 出图
       │
       ▼
[ CopywritingAgent ] Temperature=0.85
   - 组合：产品数据 + 行业摘要 + 竞品对比 + 营销模板
       │
       ▼
[ 输出：HTML5 落地页 + 多平台推文 ] ──► 回流为新内容资产
       │
       ▼
[ 产出内容可再次入库 ] → 供 SEO、客服话术、其他模块复用（飞轮）
```

### 7.2 关键设计：知识资产飞轮

录入产品 → 自动入 RAG → 内容生成调用产出营销页/文案 → 产出内容回流入库 → 又成为新素材。这样"录一次产品"可被无限次复用，且产出可供其他模块（SEO、私域、推送）调用。

内容生成调用产品的方式是**统一工具接口**：内容生成模块不直接读数据库，而是调用与客服相同的 `search_products` / `kb_search` MCP 工具，仅切换为发散模式参数。这保证了"一次接入多处复用"。

## 十、工程保障与风险

### 10.1 工程优化要点

- **算力底座**：生产强制 x86 + NVIDIA GPU，`.env` 开 `DEVICE=gpu`、`MAX_CONCURRENT_TASKS=4`；纯文本走 `naive` 绕过 DLR/TSR，释放 GPU 给规格 PDF。
- **MCP 容错**：工具层加 `execution_timeout`（如 1.5s）+ 异常捕获，超时自动降级到缓存，避免对话死锁。
- **全链路可观测**：网关植入 `X-Request-Trace-ID`，AgentScope 集成 OpenTelemetry + Langfuse，树状耗时秒级定位瓶颈。

### 10.2 主要风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 解析质量差导致检索不准 | 客服幻觉 | DeepDoc 高保真 + 父子分块 + 人工抽检 |
| 结构化数据时效滞后 | 报错价格/库存 | MCP 实时轨直连只读库，0 延迟 |
| 增量钩子失败漏同步 | 知识库陈旧 | 定时游标轮询兜底，最终一致 |
| LLM 越权提取参数 | 查询异常 | enum 约束 Schema + 参数校验 + 熔断 |
| 客服与生成需求冲突 | 体验割裂 | 双模参数调控，一套底座两种人格 |

## 附录：术语速查

- **RAGFlow**：深度文档理解的 RAG 引擎（DeepDoc 解析、分块、混合检索）。
- **AgentScope**：阿里开源生产级多智能体框架（ReActAgent、Toolkit、Code Sandbox）。
- **MCP**：Model Context Protocol，标准化工具调用协议，安全暴露数据库/服务。
- **父子分块**：父块保语义、子块保精度，检索命中子块返回父块上下文。
- **查询改写（Query Rewrite）**：检索前对用户问题做指代消解/纠错/术语对齐，缩小"问题-文档"语义鸿沟。
- **HyDE（假设文档嵌入）**：先让 LLM 生成"假设答案"再用其向量检索，把非对称匹配转为文档-文档对称匹配。
- **Doc2Query（反向问题生成）**：离线为每个 chunk 预生成可回答的问题并索引，提升口语提问召回、不增加实时延迟。
- **Cross-Encoder（交叉编码器）**：Rerank 精排模型，把 Query 与文档拼接后用交叉注意力精判相关性。
- **RAPTOR**：多级递归摘要聚类，支持先看摘要再下钻的多跳检索。
- **GraphRAG**：构建实体关系图谱辅助检索，支撑跨文档/跨标准推理。
- **Checkpoint Pull / Push**：游标增量轮询 / 主动事件推送两种同步方式。
