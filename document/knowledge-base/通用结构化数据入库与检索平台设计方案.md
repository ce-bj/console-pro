# 通用结构化数据入库与检索平台设计方案

## 1. 设计目标

本平台面向多租户场景。不同客户的数据结构、业务类型和字段含义均不确定，平台需要支持商品、文章、酒店、招聘、课程、门店、企业、房产等不同类型的结构化数据，并在数据入库后提供统一的检索能力。

整体设计目标：

- 支持客户上传不同结构的结构化数据
- 平台统一管理字段类型和字段能力
- 平台提供默认规则和自动推荐，降低用户配置成本
- 支持关键词搜索、条件筛选、聚合筛选、排序、结果展示和 AI 语义检索
- 平台侧保证能力覆盖度，用户侧保证配置简易度
- 字段类型与搜索能力解耦，便于后续扩展新的业务字段

核心设计原则：

> **Field Type + Capability + Default Policy + User Override**

即：

1. 平台定义字段类型
2. 平台定义字段可以具备哪些能力
3. 平台为不同字段类型提供默认能力
4. 用户根据自己的业务需求覆盖默认配置

---

# 2. 总体架构

平台中的核心对象建议抽象为：

```text
Tenant
│
├── Dataset
│   ├── Records
│   ├── Fields
│   ├── Schema
│   └── Search Config
│
└── Tenant Settings

Platform
├── Field Templates
├── Capability Rules
├── Default Policies
└── Search Policies
```

平台不需要预先知道客户上传的是“商品”“文章”还是“酒店”。

平台只需要知道：

- 这是一个 Dataset
- Dataset 中有哪些字段
- 每个字段是什么类型
- 每个字段具备什么检索能力

| 平台字段 | 底层数据类型 |
|---|---|
| 单行文本 | string |
| 多行文本 | text |
| 富文本（详情） | richtext / text |
| 富文本（简要） | text |
| 单选框 | enum |
| 多选框 | enum[] |
| 下拉单选 | enum |
| 下拉多选 | enum[] |
| 日期 | datetime |
| 日期区间 | date_range |
| 数值 | number |
| 图片 | asset |
| 文件 | asset |
| 视频 | asset |
| 标签 | string[] |
| 评分 | number |
| 滑动条 | number |
| 图片组 | asset[] |

这样可以避免底层搜索引擎直接依赖产品字段名称。

# 5. 统一字段能力模型

平台建议统一使用以下 6 个字段能力。

## 5.1 Searchable：可搜索

表示字段内容是否参加关键词全文搜索。

适合：

- 商品名称
- 标题
- 简介
- 描述
- 富文本正文
- 标签

产品侧建议显示为：

> **可搜索**

---

## 5.2 Filterable：可筛选

表示字段是否可以作为查询条件。

例如：

```text
品牌 = Apple
价格 >= 5000
分类 = 手机
状态 = 已发布
```

适合：

- 分类
- 品牌
- 状态
- 日期
- 数值
- 国家/地区
- 库存

产品侧建议显示为：

> **可筛选**

---

## 5.3 Facetable：可聚合

表示是否可以按照字段值统计数量，并生成前台筛选项。

例如：

```text
品牌

Apple      125
Huawei      98
Xiaomi      76
```

适合：

- 分类
- 品牌
- 标签
- 单选
- 多选
- 国家/地区
- 评分

产品侧建议显示为：

> **生成筛选项 / 聚合**

---

## 5.4 Sortable：可排序

表示字段是否可以作为排序依据。

例如：

- 价格从低到高
- 价格从高到低
- 最新发布
- 评分最高
- 销量最高

适合：

- 数值
- 日期
- 评分
- 滑动条
- 库存
- 价格

产品侧建议显示为：

> **可排序**

---

## 5.5 Retrievable：结果返回

表示搜索接口返回结果时，是否允许返回该字段。

例如：

```json
{
  "title": "iPhone",
  "price": 8999,
  "thumbnail": "...",
  "url": "..."
}
```

产品侧不建议使用 Retrievable 这个技术词。

建议显示为：

> **结果展示**

---

## 5.6 Embeddable：参与 AI 检索

该能力是平台建议额外增加的。

用于控制字段是否参与：

- Embedding
- Vector Search
- AI Search
- RAG
- Agent 检索

适合：

- 标题
- 描述
- 正文
- 摘要
- 标签
- 部分分类字段

产品侧建议显示为：

> **AI 搜索**

---

# 6. Stored 是否需要暴露

不建议面向普通用户提供 `Stored` 配置。

Stored 更偏向搜索引擎内部的数据存储策略，例如：

- 搜索引擎是否保存字段原值
- 是否只保存索引
- 是否需要额外占用存储空间

这属于底层工程实现，而不是业务用户真正关心的能力。

因此平台用户侧建议只保留：

```text
Searchable
Filterable
Facetable
Sortable
Retrievable
Embeddable
```

# 8. 平台页面设计

平台侧的目标是：

> **保证能力覆盖度，而不是追求操作简单。**

平台管理员可以看到完整能力。

建议平台后台设置分为以下几个模块。

## 8.1 字段类型管理

页面：

```text
平台设置
└── 字段类型
```

管理内容：

- 字段名称
- 字段分类
- 底层数据类型
- 是否启用
- 是否允许为空
- 最大长度
- 默认值
- 数据格式
- 支持的字段能力

例如：

```text
单行文本

底层类型：String

允许能力：
✓ 搜索
✓ 筛选
✓ 聚合
✓ 排序
✓ 展示
✓ AI
```

注意：

> “支持某种能力”与“默认开启某种能力”需要分开。

# 9. 平台默认检索规则

页面：

```text

✓ AI

○ 聚合

```

# 10. 自动推荐规则

为了减少用户配置，平台建议建立自动推荐机制。

推荐规则不仅依据字段类型，也可以依据数据特征。

## 10.1 根据字段长度

例如：

```text
平均长度 < 100
```

推荐识别为：

```text
短文本
```

默认：

```text
搜索 + 筛选 + 展示
```

如果：

```text
平均长度 > 200
```

推荐：

```text
长文本
```

默认：

```text
搜索 + 展示 + AI
```

---

## 10.2 根据唯一值比例

例如：

```text
brand

总记录：100000
唯一值：32
```

说明基数较低。

推荐：

```text
筛选 + 聚合
```

但：

```text
product_name

总记录：100000
唯一值：99800
```

则不应该推荐：

```text
聚合
```

---

## 10.3 根据字段名称

可通过字段名称提供弱推荐。

例如：

```text
price
amount
cost
```

推荐：

```text
Number
筛选
排序
```

字段包含：

```text
created_at
updated_at
date
time
```

推荐：

```text
Date
筛选
排序
```

字段包含：

```text
description
content
detail
summary
```

推荐：

```text
搜索
AI
```

# 17. 推荐的用户操作流程

用户创建数据集后建议采用：

```text
创建数据集
    ↓
配置字段 / 上传数据
    ↓
系统自动分析字段
    ↓
生成推荐配置
    ↓
用户确认或调整
    ↓
搜索预览
    ↓
发布
```

尽量避免让用户经历：

```text
创建 Schema
↓
配置 Mapping
↓
配置 Analyzer
↓
配置 Facetable
↓
配置 Filterable
↓
再上传数据
```

平台应该承担绝大部分技术配置工作。

# 19. 特殊字段处理

## 19.1 分类

分类建议采用结构化树形数据。

例如：

```json
{
  "id": "cat_1001",
  "name": "手机",
  "path": [
    "数码",
    "手机"
  ]
}
```

支持：

```text
数码
└── 手机
    ├── iPhone
    └── Android
```

这样可以实现：

- 分类筛选
- 分类聚合
- 父级分类查询
- 面包屑展示
- 分类层级检索

---

# 20. 地址

地址不建议只保存完整字符串。

建议：

```json
{
  "country": "中国",
  "province": "北京",
  "city": "北京",
  "district": "朝阳区",
  "address": "xxx路xxx号",
  "lat": 39.9,
  "lng": 116.4
}
```

可以支持：

- 国家筛选
- 省市区筛选
- 地址关键词搜索
- 附近搜索
- 距离排序

---

# 21. 关联数据

例如：

```text
商品
↓
关联
品牌
```

业务数据库中建议保存：

```json
{
  "brand_id": "brand_001"
}
```

搜索索引中可以反范式保存：

```json
{
  "brand_id": "brand_001",
  "brand_name": "Apple"
}
```

这样既保持业务数据关系，又方便搜索。

---

# 22. 子表单

子表单本身不直接定义搜索能力。

应由子字段分别配置。

例如：

```text
商品
└── SKU
    ├── 颜色
    ├── 尺寸
    ├── 价格
    └── 库存
```

可配置：

```text
SKU.颜色
→ 筛选 + 聚合

SKU.尺寸
→ 筛选 + 聚合

SKU.价格
→ 筛选 + 排序

SKU.库存
→ 筛选
```

因此：

> **子表单是一个字段容器，搜索能力属于子字段。**

---

# 23. 图片、文件、视频

图片、视频等媒体字段本身通常不参与普通文本检索。

默认建议：

```text
图片
→ 展示

图片组
→ 展示

视频
→ 展示

文件
→ 展示
```

如果未来平台支持：

- OCR
- 文件解析
- 图片理解
- 视频字幕解析

则可以增加“解析内容”作为隐藏字段参与：

```text
Searchable
Embeddable
```

即：

```text
文件
↓
解析
↓
提取文本
↓
隐藏文本字段
↓
关键词搜索 / AI Search
```

# 24. 平台与用户的职责边界

## 平台管理员负责

平台管理员关注：

- 支持哪些字段类型
- 字段底层数据类型
- 字段允许哪些能力
- 每种字段默认开什么能力
- 自动推荐规则
- 搜索引擎索引策略
- Embedding 策略
- 安全限制
- 字段数量限制
- 数据大小限制

核心目标：

> **保证平台能力覆盖度。**

---

## 租户用户负责

用户关注：

- 我的字段叫什么
- 字段是什么类型
- 哪些字段允许搜索
- 哪些字段允许筛选
- 哪些字段参与排序
- 哪些字段展示
- 哪些字段参与 AI 搜索

核心目标：

> **只做业务选择，不理解搜索引擎。**

# 26. 最终产品原则

整个方案最终可以总结成四句话：

### 1. 平台定义字段模板

例如：

```text
单行文本
分类
地址
库存
标签
评分
```

字段模板负责描述：

> 这个字段是什么。

---

### 2. 平台统一定义字段能力

统一能力固定为：

```text
Searchable
Filterable
Facetable
Sortable
Retrievable
Embeddable
```

分别对应：

```text
搜索
筛选
聚合
排序
展示
AI 搜索
```

---

### 3. 平台给出默认配置

例如：

```text
富文本
→ 搜索 + 展示 + AI

分类
→ 搜索 + 筛选 + 聚合 + 展示

价格
→ 筛选 + 排序 + 展示

库存
→ 筛选 + 排序 + 展示

图片
→ 展示
```

---

### 4. 用户只进行业务覆盖

用户无需理解底层技术。

只需要回答：

```text
这个字段：

要不要被搜索？
要不要作为筛选条件？
要不要生成筛选项？
要不要支持排序？
要不要展示？
要不要给 AI 使用？
```

因此最终的平台设计模型为：

> **Field Type + Capability + Default Policy + User Override**

这套模型能够兼容当前已有的字段体系，也能保证后续继续扩展商品、酒店、文章、招聘、房产、课程、门店等不同类型的数据，而无需重新设计底层检索架构。
